Case Study · Fall 2023—Summer 2024

Node Hub An End-to-End Process Monitoring Platform

Monitoring three stages of an anaerobic digestion prototype—from sensor readings to storage, visualization, backups, and secure remote access.

Client
Swinergy, Inc. ↗
Role
Technical Advisor

Overview

Problem

Swinergy was validating a patented, three-stage anaerobic digestion process in a small-scale lab replica to reduce the technical risk of its full-scale build. Collecting readings manually was tedious, and maintaining a consistent hourly cadence required team members to check the process at odd hours, including overnight through remote cameras. For a small team with limited capacity, time spent collecting data was time not spent improving the process.

Solution

I designed and deployed a monitoring platform that collected sensor readings at configurable intervals, stored them in a database, moved backup data files to cloud storage, and gave the team a single view of current conditions and historical trends. A secure VPN provided remote access to the platform and its sensor nodes.

Outcome

The deployed platform enabled remote monitoring and replaced manual data recording with an automated, reliable process. The successful prototype reduced the technical risk of scaling the process and supported Swinergy’s move toward its first full-scale facility.

<$1K incremental monitoring hardware, excluding existing sensors
3 independently monitored process stages
5 Raspberry Pis across sensing, hosting, and secure access
4 months from the first lab deployment to V3

Hardware Design Decisions

Swinergy, like all early-stage startups, was sensitive to unnecessary capital costs. My design delivered production results for a fraction of the cost.

Raspberry Pis are inexpensive Linux computers running from SD cards. The prototype used five of them, along with inexpensive cabling and an approximately $10 EZO USB carrier board for each sensor. The incremental monitoring hardware cost less than $1,000. Industrial controls were a better choice for a full-scale facility, but were too expensive before the process had been proven.

The Hub was containerized so it was easily portable from the initial Raspberry Pi hardware. This decision allows it to move to a Linux thin client backed by an uninterruptible power supply—a better long-term host for the database and central application—without changing the deployment model.

Software + Network Architecture

Three sensor nodes collected readings from the tanks. The Hub scheduled collection, stored the data, and served the dashboard. WireGuard provided remote access without exposing the application or sensor APIs to the internet.

Iterative Development

From February through June 2024, operator feedback and real hardware failures drove changes to recovery and configuration.

  1. Fall—Dec 2023

    Discovery

    Mapped the manual workflow, lab constraints, sensors, process stages, and required data.

  2. Feb 2024 · V1

    V1 Deployed

    The first sensor server maintained long-lived hardware connections. EZO carrier serials were configured in both the Hub and sensor server, so replacing a carrier required changes in two places. When a stale connection could not recover, the Pi restarted and systemd brought the API back automatically.

  3. Spring 2024

    Support and Iteration

    Updates separated sensor failures from node failures, improved visibility into unreachable hardware, and removed duplicated carrier configuration.

  4. Summer 2024 · V3

    V3 Deployed

    The Hub became the sole owner of fleet configuration and carrier-to-role mapping. Sensor servers discovered the EZO USB carriers attached to each Pi and served their readings. Individual connections could recover without restarting the node.

Discovers FTDI-based Atlas Scientific EZO pH and RTD circuits, manages hardware communication and per-device recovery, and exposes serial-addressed readings through FastAPI.
